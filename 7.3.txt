# Phase 7.3 - Per-Member Workload Drill-Down

## STATUS
COMPLETED

## OBJECTIVE
Extend the Dashboard's per-group productivity (7.2) with a per-member workload drill-down:
for every member of a group, their assigned-task stats (total / to do / in progress /
completed / overdue / due soon / completion rate) plus an "Unassigned tasks" bucket —
computed server-side in one aggregation query, shown as an expandable inline sub-table.

## WHAT WAS IMPLEMENTED

### Backend (7.2 `?include=stats` precedent, applied to the members endpoint)
`GET /api/groups/:id/members?include=stats` →
```json
{ "members": [ { ..., "role": "member", "user": {...},
                 "stats": { "total": 6, "todo": 3, "inProgress": 1, "completed": 2,
                            "overdue": 1, "dueSoon": 1, "completionRate": 33 } } ],
  "unassigned": { "total": 3, "todo": 2, "inProgress": 0, "completed": 1,
                   "overdue": 1, "dueSoon": 0, "completionRate": 33 } }
```
- `groupController.getGroupMembers`: the existing membership check runs FIRST (unchanged,
  blind 404); after the members query, when `include=stats`, ONE additional
  `Task.findAll({ where: { groupId }, attributes: ['assigneeId','status','dueDate'] })`
  is bucketed in JS by assigneeId (null → unassigned bucket). **The endpoint stays at
  exactly 3 queries regardless of member/task count — no per-member or per-task query loops.**
- Zero-task members appear with zero stats (the point: see who has no work).
- `unassigned` (top-level, only with the param) uses the same derivation; its `todo`
  equals the 7.2 group-level open-unassigned count (cross-endpoint consistency asserted).
- **Refactor**: extracted shared `computeTaskStats(tasks, now)` from `computeGroupStats`;
  group stats now = computeTaskStats + open-unassigned count. Output shape/key order of
  `computeGroupStats` preserved EXACTLY (the 7.2 productivity suite asserts strict JSON
  equality — re-run green).
- Without the param the response shape is byte-identical to before (GroupDetail member
  management and every existing consumer unaffected).

### Frontend
- `services/api.js`: `groupApi.getMembers(id, params)` accepts optional params.
- `pages/Dashboard.jsx`: accordion drill-down in the "Team Productivity by Group" table —
  one group expanded at a time (bounded state/requests), fetched once per expansion and
  cached for the page lifetime. Chevron toggle (lucide-react, already a dependency) with
  `aria-expanded`/`aria-controls`/dynamic `aria-label`; full-width colSpan=10 detail row
  contains the nested "Member workload — <group>" table: member name + role badge
  (getRoleColor), counts (Overdue red when > 0, Due Soon orange when > 0), completion
  progress bar (`role="progressbar"` + aria-valuenow/min/max/label per member per group),
  and a distinct italic gray "Unassigned tasks" bucket row shown only when it has tasks.
- States: inline loading spinner (role="status"), inline error + Retry (role="alert") that
  clears the cache and refetches, "No members." defensive empty, "—" cells when stats
  absent (older backend). All 7.1/7.2 cards, columns, links, and progress bars preserved.

## SECURITY / AUTHORIZATION VERIFICATION
- Blind-404 membership contract preserved: the existing check runs before anything new;
  non-members get 404 with zero member/task data (asserted).
- Identity fully server-derived: stats computed for ALL group members from DB rows; the
  endpoint accepts no user identity — forged `userId` param ignored (asserted).
- Cross-group isolation: member stats in group A count only group A tasks, even for users
  in multiple groups (asserted via two-group fixture).
- Aggregated data is the same the user could already page through via
  GET /api/groups/:id/tasks — no new exposure surface.
- Unauthenticated → 401 on both param variants (asserted).

## PERFORMANCE / QUERY STRATEGY
- Drill-down endpoint: exactly 3 queries total (membership check + members query + ONE
  attributes-only Task aggregation query), independent of member/task count — same bounded
  strategy as 7.2 (single query, JS bucketing). No N+1, no per-member loops.
- Frontend: one request per group expansion, cached; one group open at a time.

## KNOWN LIMITATIONS
- Snapshot only (mount-time); no realtime workload updates (consistent with 7.1/7.2).
- Per-group by design — no combined cross-group per-member view (out of scope).
- Server member order preserved (role DESC, joinedAt ASC); no client-side member sorting.
- Unassigned bucket row hidden when it has zero tasks (declutters; totals remain consistent).
- Tables scroll horizontally on narrow viewports (overflow-x convention; Phase 9 for redesign).
