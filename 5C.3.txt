COMPLETED

## OBJECTIVE
Implement the notifications REST API (7 endpoints), trigger logic in existing task/message controllers, notification preferences, and the daily deadline-approaching job, per the 5C.1.txt design and the 5C.2.txt database layer.

## WHAT WAS IMPLEMENTED

### 1. Shared Notification Service (`backend/src/utils/notificationService.js`)
- `NOTIFICATION_TYPES` - re-exported from Notification model
- `PREFERENCE_KEYS` / `DEFAULT_PREFERENCES` - mapping of notification type to preference key (taskAssigned, taskCompleted, newMessage, deadlineApproaching, mention), all default true
- `extractMentions(content)` - regex `/@([a-zA-Z0-9_]+)/g`, returns unique usernames
- `createNotification(data)` - wrapped create; logs and returns null on failure (never throws)
- `notifyUsers({ recipientIds, senderId, type, title, message, taskId, groupId, messageId, metadata })`:
  - deduplicates recipient IDs, excludes the sender (system notifications use senderId=null)
  - bulk-loads recipients' preferences; skips users who disabled that notification type
  - creates one notification per recipient; failures logged, never thrown
- `sanitizeNotification(notification)` - response shape per 5C.1 section 6 (includes sender/task/group objects + metadata)

### 2. Notification Controller (`backend/src/controllers/notificationController.js`) - 7 endpoints
| Endpoint | Handler | Notes |
|----------|---------|-------|
| GET /api/notifications | getNotifications | page/limit (1-100, clamped)/isRead/type/before cursor filters; ordered createdAt DESC; returns `{ items, pagination }` with hasMore |
| GET /api/notifications/unread-count | getUnreadCount | `{ unreadCount }` |
| PUT /api/notifications/:id/read | markAsRead | ownership enforced via recipientId=me; sets isRead=true, readAt=now; returns sanitized item |
| PUT /api/notifications/read-all | markAllAsRead | bulk update for current user only; returns updatedCount |
| DELETE /api/notifications/:id | deleteNotification | ownership enforced; hard delete |
| GET /api/notifications/preferences | getPreferences | merges stored prefs over defaults |
| PUT /api/notifications/preferences | updatePreferences | validates keys (unknown -> 400) and boolean values; merges and persists |

### 3. Routes (`backend/src/routes/notifications.js`, mounted in routes/index.js)
- Mounted at `/notifications` BEFORE the `/` mounted routers so paths resolve correctly
- Static routes defined before parameterized ones (unread-count, read-all, preferences)
- `router.use(authenticate)` on all routes

### 4. Triggers in taskController.js
- **assignTask** → after successful assignment: TASK_ASSIGNED to new assignee (skipped when self-assign). Title "New task assigned", message includes task title + group name, metadata per design.
- **updateTaskStatus** → on transition to 'completed' (captured BEFORE update to avoid in-instance mutation bug): TASK_COMPLETED to creator + assignee + TaskMembers(role='follower'), excluding actor.

### 5. Triggers in messageController.js
- **addGroupMessage** → NEW_MESSAGE to all group members except sender ("{senderName}: {first 100 chars}"); @username mentions resolved against group members get MENTION instead of NEW_MESSAGE (precedence rule, documented below).
- **addTaskComment** → NEW_MESSAGE to creator + assignee + TaskMembers(followers) except sender ("New comment on {taskTitle}"); mentions scoped to group members get MENTION.
- All trigger code is inside try/catch: a notification failure never fails the primary message/comment action.

### 6. Deadline Job (`backend/src/jobs/deadlineNotificationJob.js`)
- `runDeadlineCheck()` - finds tasks with dueDate within next 24h and status NOT IN ('completed','overdue'); creates DEADLINE_APPROACHING for assignee+creator (senderId=null = system); dedupes via existing DEADLINE_APPROACHING notification for same taskId within last 24h; respects recipient preferences.
- `startDeadlineNotificationJob()` - zero-dependency scheduler (setTimeout + setInterval, no new npm dependency): runs daily at 09:00 UTC. Started from server.js after DB connect.
- `msUntilNextRun()` helper computes delay to next 09:00 UTC.

### 7. Preferences storage (additive schema change)
The 5C.1 design specifies GET/PUT preferences endpoints whose settings must filter triggers (5C.1 sections 6, 15, 17), but its schema defines no storage for them. To make the designed endpoints functional, added:
- Migration `20240821190008-add-notification-preferences-to-users.js`: nullable JSON column `notificationPreferences` on Users
- `User.notificationPreferences` field (JSON, allowNull, default null = all defaults enabled)
This is additive and does not alter the Notifications table implemented in 5C.2.

## DESIGN DECISIONS & NOTES

1. **MENTION precedence**: A user mentioned in a message/comment receives MENTION only, not also NEW_MESSAGE, avoiding duplicate pings for the same content. (Design lists both types but does not define overlap behavior.)
2. **Trigger isolation**: notifyUsers/createNotification swallow+log errors so notification problems can never break task assignment, completion, or messaging.
3. **Follower scope**: Per 5C.1 ("TaskMembers role: follower"), only TaskMember rows with role='follower' are notified on completion/comments (assignee/reviewer roles excluded as they are covered by creator/assignee rules or not specified).
4. **No cron dependency**: scheduling uses plain timers; swapping to node-cron later is isolated to startDeadlineNotificationJob().
5. **updateTask direct assignee change** intentionally does NOT fire TASK_ASSIGNED (design specifies the trigger on PUT /api/tasks/:id/assign only).
6. **Pre-existing quirk documented, untouched**: taskController.updateTask contains a stray duplicated `module.exports = {...}` statement mid-function (harmless expression statement; final exports at file end are authoritative). Left unmodified per "do not modify unrelated features".

## KNOWN ISSUES
1. **Server process lifetime in dev shell**: background server processes die when their parent shell exits (pre-existing environment issue, unrelated to this phase); production should use a process manager.
2. **JWT expiry 15 min**: pre-existing; long-lived sessions need refresh tokens (Phase 9 candidate).
3. **updateTask assignee changes don't notify**: by design scope (trigger specified only for /assign endpoint).
4. **Stray module.exports statement inside updateTask**: pre-existing harmless artifact in taskController; left untouched.
5. **Real-time delivery**: polling-based until Phase 5D Socket.IO integration.
