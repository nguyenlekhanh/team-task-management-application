## IMPLEMENTATION SUMMARY

### New backend modules
**`src/socket/presence.js`** — in-memory registry `Map<userId, { sockets:Set<socketId>, generation:number, offlineTimer }>`:
- `addSocket(userId, socketId)` → 0→1 transition broadcasts online once; 1→N adds silently (multi-tab correct)
- `removeSocket(userId, socketId)` → other sockets remaining ⇒ nothing; last socket gone ⇒ grace timer starts
- **Generation guard**: every transition increments a per-user generation captured by its timer; on fire, offline is applied only if generation still matches AND socket set is still empty — a stale timer can never mark a reconnected user offline (double protection alongside clearTimeout-on-reconnect)
- Broadcasts `presence:updated` to co-member group rooms only (`GroupMember` lookup per transition); best-effort try/catch — failures logged, never affect socket lifecycle
- `evictUserFromRoom/evictUserFromGroup(userId, room)` — leaves ALL of the user's sockets from a room via the registry (multi-tab correct); no-op-safe before init

**`src/socket/joinLimiter.js`** — bounded in-memory fixed-window limiter keyed `${userId}:${event}`:
- Defaults 20 joins / 10 s (env knobs `SOCKET_JOIN_LIMIT`, `SOCKET_JOIN_WINDOW_MS`)
- Opportunistic pruning of expired entries + hard size cap (10k) against unbounded growth
- `clearUser()` on socket disconnect → reconnects never inherit stale counters

### Wiring (`src/socket/index.js`)
- Connection: implicit `user:{id}` join + `presence.addSocket()`; Disconnect: `presence.removeSocket()` + `joinLimiter.clearUser()`
- `group:join` / `task:join` now pass through the limiter FIRST (abuse shield incl. unauthorized spam), then run unchanged database authorization — rate limiting never replaces membership validation; throttled requests never touch the DB

### Membership-change eviction (`src/controllers/groupController.js`)
- `removeMember`: after authoritative DB deletion → evict ALL target-user sockets from `group:{groupId}` (best-effort, logged)
- `deleteGroup`: after cascade delete → evict every former member's sockets from the deleted group's room
- Re-adding membership requires a fresh authorized `group:join`; removed users cannot rejoin until the DB says so again

### Frontend
No changes required (per §17 of the phase spec): no member-list/presence UI exists today, so the realtime contract + tests were prioritized over speculative UI. Existing lifecycle already satisfies §18 (one socket/tab via SocketContext, auto-cleanup listeners, logout closes, StrictMode-safe ref guard) as proven by 5D.3/5D.4 suites.

## PRESENCE ARCHITECTURE DECISIONS

| Decision | Choice | Rationale |
|---|---|---|
| Source of truth | server-side connection registry | clients never claim presence; no client-set commands exist (`presence:setOnline` etc. ignored — tested) |
| `User.onlineStatus` DB field | NOT written by connections | inspection showed it is a user-controlled profile flag ("Show as online" toggle in Profile), not connection-derived; avoiding per-connection DB writes follows the phase's DB-discipline rule |
| Grace period | `PRESENCE_GRACE_MS` env, default 5000 ms | configurable for fast tests (suite runs at 800 ms) without leaking test-only code |
| Event | `presence:updated` S→C | matches established `<domain>:<past-tense>` convention |
| Payload | `{ userId, online, at }` | minimal; ISO timestamp per project convention; no socket IDs/secrets |
| Scope | co-member group rooms only | smallest correct audience; unrelated/isolated users receive nothing (tested) |
| Initial snapshot / resync | not added | no consumer exists yet; reconnect correctness is covered by REST-authoritative resync patterns from 5D.3/5D.4; adding a snapshot API now would be unused surface |

Event: `presence:updated` — direction S→C — room(s) `group:{gid}` of every group the subject belongs to — payload `{userId:int, online:bool, at:ISO}` — timing: on 0→1 transition (online) and after grace expiry with zero sockets (offline) — authorization: receivers are current members by virtue of room membership.

## SECURITY VERIFICATION
- Presence identity derives solely from handshake-JWT-authenticated `socket.userId`; no client command can set or spoof presence (unknown events ignored — tested).
- Broadcasts carry only `{userId, online, at}` — no socket IDs, tokens, or private fields (asserted).
- Visibility limited to co-members via existing group rooms; isolated users receive nothing (asserted).
- Removed members: evicted from all their sockets, cannot rejoin without DB-backed membership, receive no further frames (all asserted).
- Rate limiting is additive: it throttles volume only and never bypasses/replaces membership checks (asserted both directions).
- User-room and notification-room isolation intact (foundation + 5D.4 suites re-run green).

## MEMORY / PERFORMANCE REVIEW
- Registry entries deleted when grace expires with zero sockets; timers cleared on reconnect/reset.
- Limiter prunes expired windows on every check and hard-caps at 10k entries; per-user state cleared on disconnect.
- Per-transition cost: one indexed GroupMember query for broadcast fan-out — negligible at team scale.

---

## KNOWN LIMITATIONS / DEFERRALS BEYOND 5D.5
1. No presence UI yet (no consumer existed; contract + tests delivered first).
2. Single-instance only: registry/limiter/grace timers are in-memory; multi-instance deployment would require the Redis adapter plan noted in 5D.1 §14 (explicitly out of scope).
3. Presence visibility is group-scoped; cross-group "friends"/direct-message presence has no concept in this app.
4. Group-owner deletion of an offline user relies on room absence rather than active eviction (sockets reconnect into re-validated joins).
5. Phase 9 items (rate limiting on REST auth routes, CORS tightening for REST, refresh tokens) remain separate future work.
