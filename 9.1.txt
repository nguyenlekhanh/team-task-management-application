# Phase 9.1 - Refresh Tokens & Token Revocation

## STATUS
COMPLETED

## PHASE / SUB-PHASE
Phase 9: Testing and Deployment — Sub-phase 9.1: Refresh Tokens & Token Revocation
(first documented Phase 9 candidate; 5E.3 known-limitation #1, deferred consistently
across 5E.1/5E.2/5E.3/5C.3/5D.5/7.4/8.4 records)

## OBJECTIVE
Close the documented stateless-JWT gap: bearer tokens previously remained valid up to
15 minutes after logout (cookie cleared, token not revoked — pinned by a 5E.1 test as
"documented posture"). Introduced refresh tokens + a server-side revocation check so
sessions outlive the 15-minute access token, logout actually revokes, and all existing
auth semantics (blind-404, role checks, socket auth, login limiter) are preserved.

## WHAT WAS IMPLEMENTED

### Backend — new `src/services/tokenStore.js` (in-memory session store)
- Same accepted single-node pattern as presence/limiters (docs/DEPLOYMENT.md).
  Restart = all sessions invalid (users re-login) — documented trade-off, strictly
  safer than the old posture where logout did nothing server-side.
- Families: one per login session (`familyId` = `sid` claim in access tokens).
- Refresh tokens: random 256-bit ids, sha256-hashed at rest, 7-day family TTL
  (`REFRESH_TOKEN_TTL_MS` env knob), single-use rotation.
- **Theft detection**: replaying a consumed refresh token revokes the entire family
  immediately (`[AUTH]` log line); the family's still-live access tokens die too
  (short-lived tombstones outlast the ≤15-min access-token lifetime, then prune).
- Memory discipline mirrors loginLimiter/joinLimiter: opportunistic pruning of expired
  families/tombstones + 10k hard cap with oldest-shedding.

### Backend — auth changes
- `utils/tokenAuth.js` (single source of truth for REST + socket): access tokens now
  carry `sid`; a revoked/dead family ⇒ 401 'Invalid token'. **Pre-9.1 tokens (no sid)
  remain accepted** — rolling-restart compatibility; they simply can't be revoked
  (documented old posture for their remaining ≤15 min).
- `authController`: login/register create a session and return/set `token` + `refreshToken`
  (both httpOnly cookies — `token` 15m, `refreshToken` 7d, SameSite=Lax, Secure in prod —
  plus body values for the SPA's explicit calls). NEW `refresh()`: consumes the presented
  refresh token (body or cookie), rotates it, issues a fresh 15-min access token.
  Uniform 401 'Invalid refresh token' for every failure (no enumeration surface).
  `logout()` now ALSO revokes the session family when a refresh token is presented —
  backward compatible (cookie-only logout still works as before).
- `routes/auth.js`: + POST /api/auth/refresh (public, valid refresh token required).
- Access tokens gained a `jti` claim (uniqueness; rotation within the same second
  previously minted byte-identical tokens).

### Frontend
- `services/api.js`: response interceptor — protected-request 401 'Token expired' now
  attempts ONE silent refresh + retry (single-flight: concurrent 401s share one
  refresh call; `_retried` guard prevents loops). Refresh failure falls through to the
  existing wipe/redirect. `performSilentRefresh` exported for SocketContext.
  **The refresh token is NEVER persisted** — httpOnly cookie transport; the login/
  register body value lives only in an in-memory ref for explicit logout-with-revoke.
- `contexts/AuthContext.jsx`: login/register keep `refreshTokenRef` in memory (useRef —
  not localStorage); logout sends it so the server revokes the family.
- `contexts/SocketContext.jsx`: 'Token expired' connect_error now attempts one silent
  refresh, reconnects with the fresh token; only refresh failure falls through to the
  wipe/redirect (mirrors the REST path).

## SECURITY CONSIDERATIONS (implemented + verified)
- Refresh tokens httpOnly+SameSite=Lax (Secure in prod); never in localStorage (grep
  verified); never logged (grep verified); stored hashed server-side.
- Single-use rotation + family revocation on replay (theft detection) — unit- and
  HTTP-verified.
- Uniform refresh rejections (garbage/missing/replay all 401 'Invalid refresh token') —
  no token-state enumeration.
- Access-token exposure window unchanged (15 min); revocation check is O(1) per request
  via the shared verifier (REST + socket both inherit it).
- loginLimiter, blind-404, HS256 pinning, role checks: untouched and re-verified green.

## API CHANGES
- NEW: POST /api/auth/refresh — { refreshToken? (body) or httpOnly cookie } →
  { token, refreshToken, user } (+sets both cookies); uniform 401 on any failure.
- login/register/logout responses gain/rotate `refreshToken`; logout accepts optional
  { refreshToken } for server-side revocation. Backward compatible with all prior
  clients (cookie-only logout, sid-less tokens).

## KNOWN LIMITATIONS
- Single-node session store: no cross-process revocation (explicit DEPLOYMENT.md
  non-goal — Redis/multi-instance remains out of scope).
- Pre-9.1 tokens minted before an upgrade stay valid ≤15 min and cannot be revoked
  (rolling-restart compatibility; they expire naturally).
- Socket connections validated at (re)connect keep their mid-flight auth until
  disconnect (unchanged 5D.1 posture); REST revocation is immediate.
- The in-memory logout-with-revoke depends on the tab that holds the refresh-token ref
  or the httpOnly cookie; other tabs' stale access tokens die within ≤15 min or on
  their next 401→refresh (which then fails → wipe/redirect).
