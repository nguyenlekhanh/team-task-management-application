## VULNERABILITIES FOUND & FIXES MADE (5 real findings)

### V1 — Unrestricted CORS (medium)
- **Evidence**: `app.use(cors())` allowed every origin with credentials; browsers could send credentialed cross-origin requests from any site.
- **Fix**: origin allowlist from `CLIENT_ORIGIN` (comma-separated, default `http://localhost:5173`) applied to REST; disallowed browser origins receive no ACAO header. No-Origin requests (tests/curl) pass through. Matches the Socket.IO allowlist from 5D.2.

### V2 — JWT algorithm not pinned (low-medium)
- **Evidence**: `jwt.verify(token, SECRET)` accepted any algorithm header; enables alg-confusion token forgery classes.
- **Fix**: `algorithms: ['HS256']` pinned in `utils/tokenAuth.js` (single shared verification point for REST + sockets).

### V3 — Cookie missing SameSite (low)
- **Evidence**: auth cookie had HttpOnly + Secure(prod) but no SameSite → relied on browser defaults.
- **Fix**: `sameSite: 'lax'` added.

### V4 — No registration password minimum (low)
- **Evidence**: `POST /auth/register` accepted any password length while change-password enforced ≥6 — inconsistent policy.
- **Fix**: registration enforces ≥6 characters (`400 Password must be at least 6 characters`), aligned with existing convention.

### V5 — Login brute-force exposure (medium)
- **Evidence**: unlimited failed login attempts per IP; no throttle anywhere on auth endpoints.
- **Fix**: new `middleware/loginLimiter.js` — bounded in-memory fixed-window counter of FAILED attempts per IP (default 30 / 15 min via `AUTH_MAX_FAILED`, `AUTH_FAILURE_WINDOW_MS`); blocked IPs get 429 'Too many failed login attempts…' even for valid credentials until the window expires; successful logins never counted; pruned opportunistically + hard size cap; documented env knobs.
- **Verified live** (knobbed run): 5 failures → 429 lockout incl. correct credentials; window expiry restores access (window=2.5s run).

## KNOWN LIMITATIONS / ACCEPTED RISKS (documented, deferred to Phase 9+)
1. **Stateless JWT residual validity**: bearer tokens remain valid ≤15 min after logout/cookie-clearing; no revocation list by design (cookie IS cleared). Refresh-token/blacklist decision remains Phase 9.
2. **JWT_SECRET default fallback** ('your-secret-key') exists for dev convenience; production deployments MUST set a strong secret (documented in .env.example posture).
3. Registration username-uniqueness 409 allows username enumeration — standard trade-off, left unchanged.
4. Failed-login lockout is per-IP only; shared-NAT users can lock each other out within the window; distributed attacks are out of scope for single-instance SQLite deployment.
5. Resource limits rely on express.json's ~100 kB body cap + per-field length caps; no request-rate limiting on non-auth REST endpoints (socket joins and logins are limited).
6. HTTPS/HSTS, CSP, and reverse-proxy TLS termination belong to deployment (Phase 9 / out of code scope).
