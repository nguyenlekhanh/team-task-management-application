# Phase 5C.1 - Notifications Design & Implementation Plan

## STATUS
DESIGN COMPLETE (Planning phase only - no implementation yet)

## OBJECTIVE
Design a comprehensive notification system for the Team Task Management Application that covers in-app notifications triggered by user actions, with future compatibility for real-time delivery via Socket.IO (Phase 5D).

---

## 1. NOTIFICATION USE CASES

### Core Triggers (MVP - Phase 5C)
| Trigger | Event | Recipients | Type |
|---------|-------|------------|------|
| Task Assigned | User assigned to task (via PUT /api/tasks/:id/assign) | Assignee | TASK_ASSIGNED |
| Task Status Changed | Task marked completed (via PUT /api/tasks/:id/status) | Creator, Assignee, Task followers (TaskMembers) | TASK_COMPLETED |
| New Group Message | Message sent to group (POST /api/groups/:groupId/messages) | All group members EXCEPT sender | NEW_MESSAGE |
| New Task Comment | Comment added to task (POST /api/tasks/:taskId/comments) | Task creator, assignee, followers EXCEPT sender | NEW_MESSAGE (with task context) |
| Deadline Approaching | Daily cron job checks tasks due in 24h | Assignee, Creator | DEADLINE_APPROACHING |
| @Mention in Comment | Comment contains @username | Mentioned user (if group member) | MENTION |

### Future Enhancements (Post-MVP)
- Task overdue notification
- Task priority changed
- New member added to group
- Role changed in group
- Checklist item completed by another user
- Comment reply (threading)
- Email/push notification preferences

## 2. DATABASE SCHEMA

### Notifications Table
```sql
CREATE TABLE Notifications (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  recipientId INTEGER NOT NULL,
  senderId INTEGER NULL,
  taskId INTEGER NULL,
  groupId INTEGER NULL,
  messageId INTEGER NULL,
  type VARCHAR(50) NOT NULL,
  title VARCHAR(200) NOT NULL,
  message TEXT NOT NULL,
  isRead BOOLEAN DEFAULT FALSE,
  readAt DATETIME NULL,
  metadata JSON NULL,  -- Flexible payload: { taskTitle, groupName, mentionText, etc }
  createdAt DATETIME DEFAULT CURRENT_TIMESTAMP,
  updatedAt DATETIME DEFAULT CURRENT_TIMESTAMP,
  
  FOREIGN KEY (recipientId) REFERENCES Users(id) ON DELETE CASCADE,
  FOREIGN KEY (senderId) REFERENCES Users(id) ON DELETE SET NULL,
  FOREIGN KEY (taskId) REFERENCES Tasks(id) ON DELETE SET NULL,
  FOREIGN KEY (groupId) REFERENCES Groups(id) ON DELETE CASCADE,
  FOREIGN KEY (messageId) REFERENCES Messages(id) ON DELETE SET NULL
);
```

### Indexes
```sql
-- Primary query: unread notifications for user
CREATE INDEX idx_notifications_recipient_read ON Notifications(recipientId, isRead);

-- Primary query: paginated notifications for user (newest first)
CREATE INDEX idx_notifications_recipient_created ON Notifications(recipientId, createdAt DESC);

-- Cleanup queries
CREATE INDEX idx_notifications_created ON Notifications(createdAt);

-- Trigger queries (bulk operations)
CREATE INDEX idx_notifications_task ON Notifications(taskId);
CREATE INDEX idx_notifications_group ON Notifications(groupId);
CREATE INDEX idx_notifications_type ON Notifications(type);
```

### Notification Types (ENUM in application layer)
```javascript
const NOTIFICATION_TYPES = {
  TASK_ASSIGNED: 'TASK_ASSIGNED',
  TASK_COMPLETED: 'TASK_COMPLETED',
  NEW_MESSAGE: 'NEW_MESSAGE',       // Group message or task comment
  DEADLINE_APPROACHING: 'DEADLINE_APPROACHING',
  MENTION: 'MENTION',
};
```

## 4. NOTIFICATION TYPES - DETAILED SPECIFICATIONS

### TASK_ASSIGNED
- **Trigger**: PUT /api/tasks/:id/assign (owner/admin only)
- **Recipient**: New assignee (single user)
- **Sender**: User who performed assignment
- **Title**: "New task assigned"
- **Message**: "You have been assigned to task '{taskTitle}' in group '{groupName}'"
- **Metadata**: `{ taskId, taskTitle, groupId, groupName, assignedBy }`
- **Navigation**: Link to `/groups/:groupId/tasks/:taskId`

### TASK_COMPLETED
- **Trigger**: PUT /api/tasks/:id/status with status='completed'
- **Recipients**: Task creator, assignee, all TaskMembers (role: follower)
- **Sender**: User who marked task complete
- **Title**: "Task completed"
- **Message**: "'{taskTitle}' has been marked as completed by {senderName}"
- **Metadata**: `{ taskId, taskTitle, groupId, groupName, completedBy }`
- **Navigation**: Link to `/groups/:groupId/tasks/:taskId`

### NEW_MESSAGE (Group Chat)
- **Trigger**: POST /api/groups/:groupId/messages
- **Recipients**: All GroupMembers EXCEPT sender
- **Sender**: Message author
- **Title**: "New message in {groupName}"
- **Message**: "{senderName}: {messagePreview}" (first 100 chars)
- **Metadata**: `{ groupId, groupName, messageId, senderId, senderName }`
- **Navigation**: Link to `/groups/:groupId` (scroll to message)

### NEW_MESSAGE (Task Comment)
- **Trigger**: POST /api/tasks/:taskId/comments
- **Recipients**: Task creator, assignee, TaskMembers (followers) EXCEPT sender
- **Sender**: Comment author
- **Title**: "New comment on {taskTitle}"
- **Message**: "{senderName} commented: {commentPreview}"
- **Metadata**: `{ taskId, taskTitle, groupId, groupName, messageId, senderId, senderName }`
- **Navigation**: Link to `/groups/:groupId/tasks/:taskId`

### DEADLINE_APPROACHING
- **Trigger**: Daily cron job (runs at 09:00 UTC)
- **Recipients**: Task assignee, creator
- **Sender**: NULL (system)
- **Title**: "Deadline approaching"
- **Message**: "Task '{taskTitle}' is due in 24 hours"
- **Metadata**: `{ taskId, taskTitle, groupId, groupName, dueDate }`
- **Navigation**: Link to `/groups/:groupId/tasks/:taskId`
- **Deduplication**: Only create if not already notified for this task (track in metadata or separate table)

### MENTION
- **Trigger**: POST /api/tasks/:taskId/comments OR POST /api/groups/:groupId/messages with @username pattern
- **Recipients**: Mentioned users who are group members
- **Sender**: Message/comment author
- **Title**: "You were mentioned"
- **Message**: "{senderName} mentioned you in {groupName}"
- **Metadata**: `{ taskId?, groupId, groupName, messageId, senderId, senderName, mentionedText }`
- **Navigation**: Link to message/comment context

## 5. READ/UNREAD STATE MANAGEMENT

### State Transitions
```
CREATED (isRead=false, readAt=null)
    │
    ▼ User opens notification dropdown / clicks notification
MARKED_READ (isRead=true, readAt=timestamp)
    │
    ▼ User can mark as unread (optional future feature)
MARKED_UNREAD (isRead=false, readAt=null)
```

### Marking Read
- **Individual**: PUT /api/notifications/:id/read
- **Bulk**: PUT /api/notifications/read-all (marks all unread → read)
- **Auto-read**: When user navigates to related entity (optional UX enhancement)

### Query Patterns
- Unread count: `SELECT COUNT(*) FROM Notifications WHERE recipientId=? AND isRead=FALSE`
- Paginated list: `SELECT * FROM Notifications WHERE recipientId=? ORDER BY createdAt DESC LIMIT ? OFFSET ?`
- Filter unread: `... WHERE recipientId=? AND isRead=FALSE ...`

## 7. AUTHORIZATION RULES

| Endpoint | Permission | Notes |
|----------|------------|-------|
| GET /api/notifications | Authenticated user, owns notifications | 401 if no token, 404 if notification not found |
| GET /api/notifications/unread-count | Authenticated user | Returns count for current user only |
| PUT /api/notifications/:id/read | Authenticated user, owns notification | 404 if not owner |
| PUT /api/notifications/read-all | Authenticated user | Only affects current user's notifications |
| DELETE /api/notifications/:id | Authenticated user, owns notification | 404 if not owner |
| GET /api/notifications/preferences | Authenticated user | Returns current user's preferences |
| PUT /api/notifications/preferences | Authenticated user | Updates current user's preferences |

### Key Principles
- **Ownership**: Users can only access/modify their own notifications (recipientId = currentUserId)
- **No cross-user access**: Cannot read other users' notifications
- **Group membership not required for reading**: Notifications are personal, not group-scoped
- **Trigger authorization**: Handled in source controllers (taskController, messageController)

- **Schedule**: Daily at 09:00 UTC

- **Deduplication**: Check if notification already exists for this task+type in last 24h

## 11. INDEXING AND PERFORMANCE CONSIDERATIONS

### Critical Indexes
```sql
-- Most frequent query: user's notifications paginated
CREATE INDEX idx_notifications_user_paginated ON Notifications(recipientId, createdAt DESC);

-- Unread count query
CREATE INDEX idx_notifications_user_unread ON Notifications(recipientId, isRead);

-- Bulk operations (mark all read)
-- Uses recipientId index

-- Trigger queries (finding recipients)
-- GroupMembers: (groupId, userId) already indexed
-- TaskMembers: (taskId, userId) already indexed
```

### Query Optimization
- Always filter by `recipientId` first (highest cardinality)
- Use cursor-based pagination (`WHERE createdAt < ?`) for deep pagination
- Limit max page size to 100
- Consider partitioning by date for very large datasets (future)

### Estimated Volume
- Per user: ~100-1000 notifications typical
- Per group: ~1000-10000 messages → notifications per member
- Total: < 1M rows expected for small-medium teams
- SQLite handles this easily with proper indexes

## 12. PAGINATION STRATEGY

### Cursor-Based Pagination (Recommended)
```javascript
// First page
GET /api/notifications?limit=20

// Subsequent pages
GET /api/notifications?limit=20&before=2026-01-15T10:30:00.000Z
```

**Benefits:**
- Consistent performance regardless of page depth
- Works well with real-time inserts (no offset shift)
- Compatible with infinite scroll

### Alternative: Offset-Based (Simple)
```javascript
GET /api/notifications?page=2&limit=20
```
- Simpler to implement
- Acceptable for < 10k notifications per user
- Use for MVP, migrate to cursor if needed

### Decision
**Use cursor-based pagination** for consistency with Messages API (Phase 5B) and better UX with real-time.

## 13. CLEANUP / RETENTION CONSIDERATIONS

### Retention Policy
| Notification Type | Retention | Reason |
|-------------------|-----------|--------|
| TASK_ASSIGNED | 1 year | Reference for assignments |
| TASK_COMPLETED | 1 year | Audit trail |
| NEW_MESSAGE | 90 days | High volume, less reference value |
| DEADLINE_APPROACHING | 30 days | Time-sensitive, auto-expires |
| MENTION | 1 year | Important for collaboration |

### Cleanup Strategy
- **Soft delete**: Add `deletedAt` column, filter in queries
- **Hard delete cron**: Monthly job deletes notifications older than retention period
- **User-initiated**: DELETE endpoint for manual cleanup
- **Cascade**: When User deleted → notifications CASCADE deleted (FK)
- **Task/Group deleted**: SET NULL on taskId/groupId, keep notification for context

### Storage Estimate
- Avg notification: ~500 bytes
- 1000 users × 500 notifications = 500K rows = ~250 MB
- Well within SQLite limits

## 14. SECURITY CONSIDERATIONS

### Data Protection
- **No sensitive data** in notification message/metadata (no passwords, tokens)
- **User IDs only** in metadata, not emails/PII
- **Sanitize** user-generated content in message preview (XSS prevention)

### Access Control
- **Row-level security**: All queries filter by `recipientId = currentUserId`
- **No mass assignment**: Only allow `isRead` and `preferences` updates
- **Rate limiting**: Consider on notification endpoints (prevent spam marking)

### Validation
- **Type whitelist**: Only allow defined NOTIFICATION_TYPES
- **Recipient validation**: Must be valid user ID
- **Sender validation**: Must be valid user ID or NULL (system)
- **Reference validation**: taskId/groupId/messageId must exist if provided

## 16. ERROR HANDLING

### Standard Error Responses
```json
// 401 Unauthorized
{ "error": "Authentication required" }

// 403 Forbidden (not owner)
{ "error": "Access denied" }

// 404 Not Found
{ "error": "Notification not found" }

// 400 Bad Request
{ "error": "Validation failed", "details": [...] }

// 500 Internal Server Error
{ "error": "Internal server error" }
```

### Specific Scenarios
- **Notification not found**: Return 404 (not 403) to avoid information leakage
- **Invalid type in preferences**: Ignore unknown fields, validate known ones
- **Database errors**: Log error, return 500 with generic message
- **Cron job failures**: Log, retry with exponential backoff, alert monitoring
