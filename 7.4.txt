## ISSUES FOUND
**One real defect** (the regression sweep's purpose fulfilled):

### Dangling assigneeId after group-member removal
- **Symptom (reproduced live)**: remove a member who has assigned tasks → 7.2 group total
  still counts those tasks (correct — they belong to the group), but they appear in NO 7.3
  member bucket (the user is no longer listed) and NOT in the unassigned bucket
  (assigneeId non-null) → the documented 7.3 invariant
  "member totals + unassigned total = group total" broke, and a manager could not see
  where that work went. Pre-existing data-level gap since Phase 3 (removeMember never
  touched assignments); only became observable/diagnosable once 7.3 exposed the invariant.
- **Fix (smallest safe change at the source)**: `groupController.removeMember` now clears
  `assigneeId` (sets NULL) on the removed member's still-assigned tasks in that group,
  after the authoritative membership destroy. Rationale: a group-scoped assignment ends
  with membership; the work becomes visible under "Unassigned tasks" (exactly what a
  manager needs after removing someone) and matches the app's existing FK semantics
  (Task.assigneeId is SET NULL on user deletion since Phase 4A).
  Best-effort like the 5D.5 eviction (logged, never blocks removal). Untouched: group
  deletion (cascades tasks), user deletion (FK handles it), REST contract, realtime
  events, notifications.

## FIXES MADE
- `backend/src/controllers/groupController.js` — removeMember: post-destroy, best-effort
  group-scoped unassignment (`Task.update({ assigneeId: null }, { where: { groupId,
  assigneeId: targetUserId } })`) + log line, before the existing eviction block.
