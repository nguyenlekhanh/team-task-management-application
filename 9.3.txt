## OBJECTIVE
Deliver the documented posture: TLS terminates at a reverse proxy (never in-app — zero
certificate/key material in the repo); the application gains the correct proxy/security
posture for that architecture (opt-in trust proxy, production-only HSTS, strict API CSP);

honest security-tradeoff ledger of code-enforced vs proxy-enforced controls.

## WHAT WAS IMPLEMENTED

### Application side (`backend/src/app.js`)
- **TRUST_PROXY opt-in** (default unset = today's direct-exposure behavior, no spoofing
  surface): `TRUST_PROXY=1` (hop count) | `loopback` | CIDR → `app.set('trust proxy', …)`
  so req.ip reflects the real client behind OUR proxy and X-Forwarded-* is honored ONLY
  from the trusted hops (Express semantics — not blind header trust). Turns the 9.2
  documentation note into a supported explicit configuration.
- **Production-only security headers** (beside the untouched 5E.3 trio, gated on
  `NODE_ENV === 'production'`):
  - `Strict-Transport-Security: max-age=31536000` — conservative: **no preload, no
    includeSubDomains** (nothing in the project justifies them; both can brick
    sibling subdomains). Proxy config uses the SAME max-age so headers never contradict.
  - `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'` — exact for a
    JSON API (loads nothing, embeds nothing, frames nothing). No unsafe-inline/eval.
- **Development emits NEITHER** (HSTS over plain HTTP is wrong and could pin browsers
  to a non-TLS local origin; CSP would fight Vite's HMR) — env-gated, unit-verified.
- Secure-cookie behavior unchanged (already `NODE_ENV`-gated from 9.1) — now verified
  against the production posture by test.

### Deployment side (`docs/DEPLOYMENT.md`)
- Complete reference **nginx configuration**: HTTP:80 → 301 HTTPS redirect; TLS server
  block (TLSv1.2/1.3 only, http2); HSTS on the static side (matching max-age); the
  **minimum-viable frontend CSP** derived from the frontend audit
  (`default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline';
  img-src 'self' https: data:; connect-src 'self' <API> wss://<API>; font-src 'self';
  object-src 'none'; base-uri 'self'; frame-ancestors 'none'`); WebSocket
  `Upgrade`/`Connection` + `proxy_pass` for the app; X-Forwarded-* propagation.
- **Honest security-tradeoff ledger** (code-enforced vs proxy-enforced vs
  deploy-time-verified) and a 6-step **deployment verification checklist** (redirect,
  headers over HTTPS, CSP console cleanliness, wss:// connectivity, Secure cookies in
  browser, per-client rate-limit IPs with TRUST_PROXY).
- TRUST_PROXY row in the env table; 9.2 reverse-proxy note updated to reference it.

### Tests (`backend/tests/deployment-posture.test.js`, + `test:posture`, in `test:all`)
38 assertions in four sections:
1. Dev server (always runs): 5E.3 headers present; HSTS + CSP deliberately ABSENT —
   proves production-only behavior does not break dev/tests.
2. Production header logic (in-process, deterministic, ephemeral ports, fresh module
   graph): HSTS max-age=31536000 with no preload/includeSubDomains; strict API CSP
   (`default-src 'none'`, `frame-ancestors 'none'`, no unsafe-*); 5E.3 trio intact;
   app still plain HTTP behind the proxy; a dev instance of the same code emits neither.
3. Production cookie posture (same in-process prod instance): register Set-Cookie for
   token AND refreshToken each HttpOnly + Secure + SameSite=Lax.
4. Proxy-config static verification (grep-based, honest): doc contains listen 443 ssl,
   TLSv1.2/1.3 only (no 1.0/1.1), 301 redirect, matching HSTS (both places 31536000),
   WebSocket Upgrade/Connection directives, frontend CSP (no unsafe-eval, connect-src
   covers https + wss), proxy_pass, no private-key material (paths only), TRUST_PROXY
   guidance, and the deployment checklist.

## SECURITY IMPACT / TRADEOFFS (honest ledger summary)
- **Enforced by code**: production HSTS (conservative), strict API CSP, 5E.3 headers,
  Secure/HttpOnly/SameSite cookies, TRUST_PROXY opt-in (default off — no IP-spoofing
  regression), all prior protections (limiters ×3, blind-404, JWT + refresh rotation/
  revocation/replay detection, socket auth, error envelopes) re-verified green.
- **Enforced by the reverse proxy only**: TLS/certificates, HTTP→HTTPS redirect, HSTS +
  CSP for the static frontend, WebSocket upgrade passthrough. No certificates, private
  keys, or self-signed material exist in this repository (statically verified).
- **Verified at deployment time (checklist in DEPLOYMENT.md, NOT claimed as tested
  here)**: live redirect behavior, real TLS handshakes, CSP console cleanliness in a
  browser, wss:// connectivity, cookie flags in a real browser, per-client rate-limit
  IPs behind the proxy. No browser/proxy/production TLS testing was performed in this
  repository — stated plainly.
- **Intentionally NOT enabled in development**: HSTS (wrong over plain HTTP), API CSP
  header (Vite HMR), Secure cookie flags. All three are env-gated and test-verified.
- **Accepted tradeoffs (documented, not weakened elsewhere)**: frontend CSP needs
  `style-src 'unsafe-inline'` (3 audited React inline style props; a nonce/static-
  extraction build refactor is future work) and broad `img-src https: data:`
  (user-supplied avatarUrl rendered as <img>). The API CSP carries NO unsafe-* tokens.

## DELIBERATELY LEFT UNTOUCHED
- In-app TLS (never introduced — documented architecture)
- HSTS preload/includeSubDomains (conservative by design)
- loginLimiter/joinLimiter/restLimiter semantics; blind-404; roles; token/session flow
- Frontend code (inline styles stay; CSP accommodates them at the proxy, honestly)
- 5E.3 header trio (kept verbatim, now verified by posture suite)

## KNOWN LIMITATIONS
- Proxy config is reference nginx — not exercised in-repo; the deployment checklist
  must be run at deploy time.
- One-file-per-frontend CSP means the 3 inline styles force 'unsafe-inline' for style
  only; removing it requires a frontend build change (out of scope).
- TRUST_PROXY is deliberately NOT set by default; operators behind a proxy must set it
  or rate limits key on the proxy's IP (documented).
- The app-level API CSP is defense-in-depth only — the browser never renders API
  responses; the frontend's real CSP lives at the proxy.
